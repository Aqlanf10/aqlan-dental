أسند المهمة #1 إلى وكيل مهمة منفصل يعمل في بيئة معزولة.

قواعد التنفيذ:

1. يعمل الوكيل المنفصل على نسخة مستقلة من المستودع وعلى فرع جديد باسم:
   replit-migrations-recovery

2. لا يعدّل فرع main ولا فرع replit-development مباشرة.

3. لا يتصل بقاعدة Railway أو بأي قاعدة إنتاجية.

4. ينشئ قاعدة PostgreSQL تطويرية جديدة وفارغة ومعزولة خاصة بهذه المهمة فقط.

5. يبدأ أولًا بالبحث عن ملفات Designer.cs الأصلية في:
   - git log
   - جميع الفروع المحلية والبعيدة
   - tags
   - commits السابقة
   - Pull Requests المتاحة
   - .migration-backup
   - أي تاريخ محفوظ للمستودع

6. لا يعيد بناء أي Designer.cs قبل إكمال البحث وتوثيق النتيجة.

7. إذا عثر على الملفات الأصلية:
   - يستعيدها كما هي.
   - يذكر مصدر كل ملف والـcommit الخاص به.
   - لا يعدّل محتوى Up أو Down.

8. إذا لم يعثر عليها:
   - يعيد بناء TargetModel التاريخي لكل migration بصورة مستقلة.
   - لا ينسخ ModelSnapshot الحالي نفسه إلى الملفات الخمسة.
   - يعرض diff كاملًا قبل تطبيق أي migration.

9. يجب إنشاء checkpoint قبل أي تعديل.

10. بعد الإصلاح يشغّل:
    - dotnet restore
    - dotnet build
    - dotnet test
    - dotnet ef migrations list
    - dotnet ef migrations has-pending-model-changes
    - توليد SQL script كامل للسلسلة
    - تطبيق جميع migrations من الصفر على قاعدة الاختبار الجديدة

11. يتحقق من أن الجداول تُنشأ بالترتيب الصحيح، خصوصًا:
    - ClinicServices
    - Rooms
    - PatientJourney fields
    - TreatmentPlanSteps
    - Invoices
    - InvoiceLineItems
    - Invoice-Payment link
    - LabOrderItemsAndPricing

12. بعد نجاح السلسلة يختبر:
    - إنشاء فاتورة.
    - إضافة InvoiceLineItem.
    - ربط دفعة بالفاتورة.
    - إنشاء طلب مختبر مرتبط بالمريض والإجراء والفاتورة.
    - تسجيل تكلفة المختبر.
    - حساب سعر الخدمة على المريض.
    - خصم تكلفة المختبر والمواد قبل عمولة الطبيب.
    - منع تكرار الفاتورة أو تكلفة المختبر عند إعادة الطلب.

13. لا يستخدم EnsureCreated بدل migrations.

14. لا يحذف أو يدمج أو يعمل squash للـmigrations القديمة.

15. لا ينفذ أي migration مدمرة ولا يستخدم بيانات مرضى حقيقية.

16. في نهاية المهمة لا يدمج التغييرات تلقائيًا، بل يقدم تقريرًا ويترك الفرع للمراجعة.

التقرير النهائي يجب أن يحتوي على:

- هل عُثر على الملفات الأصلية أم أُعيد بناؤها.
- مصدر كل Designer.cs.
- جميع الملفات المعدلة.
- diff كامل.
- نتيجة dotnet build وdotnet test.
- قائمة migrations بعد الإصلاح.
- نتيجة has-pending-model-changes.
- عدد migrations التي طُبقت على القاعدة النظيفة.
- مخطط قاعدة البيانات النهائي.
- نتيجة اختبارات المالية والمختبر والربط بينهما.
- المخاطر المتبقية.
- تعليمات دمج الإصلاح بأمان في replit-development.

بعد انتهاء الوكيل المنفصل، أعِد المهمة إلى الوكيل الرئيسي لمراجعة النتائج، ثم لا تنقل أي تعديل إلى replit-development إلا بعد نجاح جميع الفحوصات.
