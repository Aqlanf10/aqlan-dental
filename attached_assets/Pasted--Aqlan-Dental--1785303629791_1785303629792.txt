المهمة الحالية الوحيدة:

فحص وإكمال وحدة المختبر وربطها بوحدة المالية داخل نفس مشروع Aqlan Dental Pro.

اعمل فقط على فرع replit-development، مع commits محلية فقط، دون push أو Pull Request أو merge إلى main.

لا تعمل على المرضى أو المواعيد أو التقويم إلا بالقدر الضروري مباشرةً لتشغيل سيناريو المختبر والمالية.

أولًا: أصلح متطلبات البيانات التجريبية

1. افحص DbSeeder الحالي.
2. أضف Seed آمنًا ومتكررًا Idempotent لـ:
   - مختبرين تجريبيين على الأقل.
   - فروع المختبر إن كان النظام يدعمها.
   - أنواع أعمال مختبرية أساسية.
   - DoctorSchedules اللازمة لتنفيذ السيناريو.
3. لا تضف بيانات مرضى حقيقية.
4. يجب ألا يكرر Seed نفس السجلات عند إعادة تشغيل التطبيق.
5. لا تستخدم إدخالات يدوية مباشرة في قاعدة البيانات كحل نهائي.

ثانيًا: افحص تدفق طلب المختبر كاملًا

تتبع العملية من:

Frontend
→ API Controller
→ Application Service/Command
→ Domain Entities
→ EF Core
→ PostgreSQL

افحص:

- إنشاء طلب مختبر.
- LabOrderItems.
- المختبر والفرع.
- المريض.
- الطبيب.
- الزيارة والإجراء.
- سعر الخدمة على المريض.
- تكلفة المختبر الداخلية.
- العملة.
- حالات الطلب.
- تاريخ الإرسال والاستحقاق والاستلام والتسليم.
- الإلغاء والإعادة للمختبر.
- Audit Log.

ثالثًا: افحص الربط مع المالية

حدد بدقة لماذا طلب المختبر لا يظهر في:

- /lab/payables
- /finance-v3
- تقارير المصروفات أو الالتزامات
- حساب ربحية الإجراء
- حساب عمولة الطبيب

تحقق هل الخلل في:

- عدم إنشاء Payable.
- عدم إنشاء Expense أو Cost entry.
- عدم ربط LabOrderId بالحركة المالية.
- عدم ربط InvoiceLineItem بطلب المختبر.
- اختلاف حالات الطلب التي تُنشئ الاستحقاق.
- خطأ في Query أو Filter.
- مشكلة صلاحيات.
- واجهة غير مرتبطة بالـAPI.
- migration موجودة لكن منطق التطبيق غير مكتمل.

رابعًا: قواعد العمل المطلوبة

اعتمد القواعد التالية:

1. سعر الخدمة المحسوب على المريض منفصل تمامًا عن تكلفة المختبر الداخلية.
2. تكلفة المختبر لا تُسجل كدفعة على المريض.
3. إنشاء طلب مختبر لا يجب أن ينشئ فاتورة مكررة.
4. إعادة الضغط أو إعادة إرسال الطلب لا يجب أن تنشئ Payable أو Cost مرتين.
5. طلب المختبر المسودة لا يدخل في الالتزامات المالية.
6. عند إرسال الطلب للمختبر أو اعتماده، تُنشأ المطالبة المالية حسب قاعدة النظام المعتمدة.
7. الطلب الملغي قبل الإرسال لا ينتج تكلفة مستحقة.
8. الإلغاء بعد الإرسال يجب أن يسجل تصحيحًا ماليًا واضحًا، لا حذفًا صامتًا.
9. إعادة العمل للمختبر يجب أن تكون قابلة للتحديد:
   - إعادة مجانية.
   - إعادة بتكلفة إضافية.
10. أي تعديل في تكلفة المختبر بعد الاعتماد يجب أن يسجل في Audit Log.
11. تكلفة المختبر والمواد تُخصم قبل احتساب عمولة الطبيب.
12. العمولة تعتمد على المبالغ المحصلة فعليًا وفق قواعد النظام الحالية.
13. جميع الحركات يجب أن تكون قابلة للتتبع عبر:
   - LabOrderId
   - PatientId
   - DoctorId
   - VisitId
   - ProcedureId
   - InvoiceId
   - InvoiceLineItemId
   - PayableId أو ExpenseId

خامسًا: سيناريو الاختبار الإلزامي

نفذ سيناريو كاملًا ببيانات وهمية:

1. تسجيل الدخول كمدير.
2. إنشاء مريض وهمي.
3. إنشاء زيارة لطبيب.
4. إضافة إجراء علاجي يحتاج عمل مختبر.
5. تسجيل سعر الخدمة على المريض.
6. إنشاء طلب مختبر من الإجراء نفسه.
7. اختيار المختبر ونوع العمل.
8. إدخال تكلفة المختبر.
9. إرسال الطلب.
10. التأكد من ظهوره في شاشة المختبر.
11. التأكد من ظهوره في /lab/payables.
12. التأكد من ظهوره في /finance-v3.
13. تسجيل دفعة جزئية من المريض.
14. التحقق من رصيد المريض.
15. التحقق من أن تكلفة المختبر لم تُحسب كدفعة للمريض.
16. التحقق من ربحية الإجراء.
17. التحقق من عمولة الطبيب بعد خصم تكلفة المختبر والمواد.
18. تغيير الطلب إلى جاهز ثم مستلم ثم مسلم.
19. اختبار الإلغاء.
20. اختبار إعادة العمل دون تكلفة.
21. اختبار إعادة العمل بتكلفة إضافية.
22. إعادة الضغط على الحفظ مرتين والتأكد من عدم التكرار.

سادسًا: الاختبارات

أضف اختبارات تمنع رجوع الأخطاء المكتشفة:

- Unit tests لمنطق التكلفة والعمولة.
- API tests لإنشاء الطلب وتغيير حالته.
- Tests لمنع التكرار Idempotency.
- Tests للصلاحيات.
- Tests للإلغاء والإعادة.
- Frontend tests لعرض Payable والتكلفة.
- اختبار تكامل باستخدام قاعدة PostgreSQL المعزولة داخل Replit بدل Testcontainers، لأن Docker غير متاح.

لا تستخدم قاعدة الإنتاج ولا Railway.

ثامنًا: تنظيم العمل

1. أنشئ Checkpoint قبل التعديل.
2. لا تعدل migrations التاريخية إلا إذا كان هناك خلل مثبت لا يمكن إصلاحه بطريقة أخرى، واعرضه أولًا.
3. لا تستخدم إدخالات SQL يدوية كحل نهائي.
4. لا تنشئ صفحات مكررة أو مسارات جديدة بلا حاجة.
5. أنشئ commits محلية محدودة، ويفضل فصلها إلى:
   - Seed data.
   - Lab-finance backend integration.
   - Frontend integration.
   - Tests.
6. لا تنفذ git push.
7. لا تغلق المهمة قبل تقديم التقرير.

معيار الإنجاز:

لا تعتبر المهمة ناجحة حتى يعمل طلب المختبر من الواجهة إلى قاعدة البيانات، ويظهر التزامه المالي مرة واحدة فقط في المختبر والمالية، وتبقى تكلفة المختبر منفصلة عن حساب المريض، وتدخل بصورة صحيحة في الربحية وعمولة الطبيب.

في التقرير النهائي اعرض:

- سبب عدم ظهور الطلبات سابقًا في payables والمالية.
- مخطط تدفق البيانات.
- الجداول والعلاقات المستخدمة.
- API endpoints.
- الملفات المعدلة.
- commits المحلية.
- عدد الاختبارات الناجحة والفاشلة.
- لقطات أو نتائج السيناريو الكامل.
- هل الربط أصبح كاملًا أم ما زالت هناك فجوات.
- النواقص المتبقية قبل الاستخدام التجريبي.
