# 001 Navigation And Module Organization Requirements

Spec ID: `001-navigation-and-module-organization`

This sprint is documentation-only. Evidence was gathered from the current repository routes, sidebar, layout guard, redirect stubs, settings hub, command center, and module map.

## Detailed Requirements

| Requirement ID | Current evidence path | Problem | Target behavior | Acceptance criteria | Runtime verification |
|---|---|---|---|---|---|
| `NAV-REQ-001` | `frontend/src/components/layout/Sidebar.tsx` | The sidebar is the single visible navigation owner, but future agents may add parallel nav files or duplicate links. | Keep one canonical staff sidebar in `Sidebar.tsx`; any extra workflow nav must be local/contextual, not another global menu. | WHEN a new visible module link is requested THEN the agent SHALL update the canonical sidebar plan/spec before code. | No |
| `NAV-REQ-002` | `frontend/src/app/(dashboard)/page.tsx`, `frontend/src/app/(dashboard)/clinic-command-center/page.tsx` | There are two admin overview concepts: dashboard `/` and command center `/clinic-command-center`. They are not identical, but they overlap in KPI/shortcut purpose. | Keep `/` as the canonical dashboard; decide whether `/clinic-command-center` remains an admin-only command overlay, is merged into `/`, or is hidden from the sidebar. | WHEN dashboard navigation is cleaned up THEN only one route SHALL be described as the main dashboard/control panel. | Yes: Needs runtime verification |
| `NAV-REQ-003` | `frontend/src/lib/routePermissions.ts`, `frontend/src/app/(dashboard)/layout.tsx` | Route guard default-denies unmatched routes, but `/` dashboard is not explicitly listed and relies on Admin bypass. | Keep default-deny; document or implement a safe explicit root handling strategy without creating a catch-all allow. | WHEN a non-admin opens `/` THEN the user SHALL be redirected to `/daily-operations`; WHEN Admin opens `/` THEN dashboard SHALL load. | Yes: Needs runtime verification |
| `NAV-REQ-004` | `frontend/src/app/(dashboard)/clinic-queue/page.tsx`, `frontend/src/app/(dashboard)/patient-journey/page.tsx`, `frontend/src/app/(dashboard)/patient-journey/[patientId]/page.tsx` | Queue and patient journey routes are redirect stubs, but direct links can still create confusing extra hops. | Treat `/daily-operations` as the canonical daily workspace; keep redirect stubs only for backwards compatibility. | WHEN a future link needs queue or journey THEN it SHALL point to `/daily-operations` or `/daily-operations?tab=queue`, not to a redirect stub. | Yes: Needs runtime verification |
| `NAV-REQ-005` | `specs/000-master-system/module-map.md`, `frontend/src/app/(dashboard)/**/page.tsx` | Module map did not fully mention `/clinic-command-center` and `/booking-requests` ownership. | Module map must include every user-facing top-level route or explain if it is a subroute/redirect. | WHEN a top-level dashboard route exists THEN module map SHALL name its owner or mark it `needs review`. | No |
| `NAV-REQ-006` | `frontend/src/components/layout/Sidebar.tsx`, `frontend/src/lib/routePermissions.ts` | `/lab/dashboard`, `/lab/reports`, and `/lab/payables` are visible to `Accountant` in the sidebar, but the first matching route permission is generic `/lab`, which excludes `Accountant`. | Add specific lab subroute permission rules before `/lab` or align sidebar roles to the guard. | WHEN Accountant sees a lab report/payables link THEN route guard SHALL allow that exact route, or the link SHALL not appear. | Yes: Needs runtime verification |
| `NAV-REQ-007` | `frontend/src/components/layout/Sidebar.tsx`, `frontend/src/lib/routePermissions.ts` | `/settings/labs`, `/settings/lab-work-types`, and `/settings/lab-pricing` are visible to `BranchManager` under the lab group, but generic `/settings` allows only Admin. | Add specific settings-lab permission rules before `/settings`, or remove BranchManager from those sidebar children until backend/frontend policy is aligned. | WHEN BranchManager sees lab settings links THEN route guard SHALL allow those exact routes, or the links SHALL not appear. | Yes: Needs runtime verification |
| `NAV-REQ-008` | `frontend/src/components/layout/Sidebar.tsx`, `frontend/src/lib/routePermissions.ts` | `/patients` route permission includes `Accountant`, but sidebar hides `/patients` from Accountant. | Decide whether Accountant needs a visible patient/account lookup path, or keep direct access only through finance patient accounts. | WHEN Accountant patient access is intended THEN navigation SHALL expose the approved path; otherwise route permissions SHALL be narrowed. | Yes: Needs runtime verification |
| `NAV-REQ-009` | `frontend/src/components/layout/Sidebar.tsx`, `frontend/src/lib/routePermissions.ts` | `/general` route permission includes `OralSurgeon`, but sidebar hides the general dentistry link from OralSurgeon. | Confirm owner intent: either expose `/general` to OralSurgeon or remove OralSurgeon from route permission. | WHEN OralSurgeon can directly open `/general` THEN sidebar and role docs SHALL explain why. | Yes: Needs runtime verification |
| `NAV-REQ-010` | `frontend/src/lib/routePermissions.ts`, `frontend/src/app/(dashboard)/ortho-surgical/page.tsx`, `frontend/src/app/(dashboard)/ortho/[id]/_components/OrthoSurgicalPlanningTab.tsx` | `/ortho-surgical` is allowed by route guard but hidden from sidebar; index redirects to `/ortho`. | Document it as a contextual shared workspace, not a sidebar module, unless owner requests a visible surgery/ortho group entry. | WHEN `/ortho-surgical` remains hidden THEN contextual links from ortho/surgery SHALL be the official access path. | Yes: Needs runtime verification |
| `NAV-REQ-011` | `frontend/src/app/(dashboard)/page.tsx`, `frontend/src/components/shared/WorkflowNav.tsx` | `WorkflowNav` links point directly to canonical daily operations, but dashboard queue card still links to `/clinic-queue`, causing an unnecessary redirect hop. | Replace future dashboard queue links with `/daily-operations?tab=queue`. | WHEN a link opens the queue from dashboard or workflow shortcuts THEN the link SHALL target the canonical daily operations tab. | Yes: Needs runtime verification |
| `NAV-REQ-012` | `frontend/src/app/(dashboard)/settings/page.tsx`, `frontend/src/app/(dashboard)/settings/_components/_shared.ts`, `frontend/src/components/layout/Sidebar.tsx` | Lab management routes appear both inside the lab sidebar group and inside the settings hub quick links. This is useful for Admin but confusing for BranchManager while permissions are misaligned. | Keep settings hub as the canonical settings surface; expose lab settings in the lab group only after route permissions and owner intent are clear. | WHEN a settings subroute appears outside `/settings` group THEN the design SHALL explain why it is operationally useful. | Yes: Needs runtime verification |
| `NAV-REQ-013` | `frontend/src/app/(dashboard)/finance-v3/page.tsx`, `frontend/src/components/layout/Sidebar.tsx` | Finance tabs are deep query-state under one route; previous duplicate sidebar entry for commissions was removed. Future agents may re-add tab-specific sidebar links. | Keep one `/finance-v3` sidebar entry. Use internal tabs and deep links only inside workflows or reports. | WHEN adding finance navigation THEN no second finance sidebar entry SHALL be added for a tab such as commissions or collections. | No |
| `NAV-REQ-014` | `frontend/src/app/(dashboard)/daily-operations/_lib/constants.ts`, `frontend/src/app/(dashboard)/daily-operations/page.tsx` | Daily operations owns appointments, queue, in-clinic, completed, payments, and overdue tabs, but some older route names remain as redirect/API concepts. | Keep daily operations tabs as the operational workflow owner and avoid new top-level daily submodules. | WHEN adding reception workflow UI THEN it SHALL extend the existing daily operations tabs or add a spec first. | Yes: Needs runtime verification |
| `NAV-REQ-015` | `frontend/src/app/(dashboard)/lab/dashboard/page.tsx`, `frontend/src/components/layout/Sidebar.tsx` | The lab dashboard label is a sub-dashboard title, which can be confused with the main dashboard/control panel. | Label module dashboards as reports/overview where practical to avoid a second-control-panel feeling. | WHEN a submodule has a dashboard page THEN its label SHALL make the module context explicit. | Yes: Needs runtime verification |
| `NAV-REQ-016` | `frontend/src/app/clinic-display/page.tsx`, `frontend/src/components/shared/WorkflowNav.tsx`, `frontend/src/hooks/usePermissions.ts` | Clinic display is outside `(dashboard)` and not a sidebar entry; it is a call/display surface rather than staff dashboard navigation. | Document `/clinic-display` as a special display route requiring runtime/security review before adding to staff nav. | WHEN clinic display is linked from staff UI THEN access assumptions SHALL be verified separately from dashboard route permissions. | Yes: Needs runtime verification |
| `NAV-REQ-017` | `frontend/src/components/layout/Sidebar.tsx` | Prescriptions currently appear after inventory and before lab, which is not the clearest clinic mental model. | Proposed final design should place prescriptions under doctor clinic/patient care or keep hidden/contextual if mostly patient-file driven. | WHEN sidebar grouping is revised THEN prescriptions SHALL be grouped by clinical workflow, not finance/inventory adjacency. | Yes: Needs runtime verification |
| `NAV-REQ-018` | `frontend/src/components/layout/Sidebar.tsx`, `frontend/src/app/(dashboard)/patient-segments/page.tsx` | Patient segments appears in the main section but behaves like patient follow-up/marketing/admin segmentation. | Confirm whether patient segments belongs under patients or communication/follow-up instead of the primary top block. | WHEN final sidebar grouping is implemented THEN patient segments SHALL be placed where clinic staff expect to use it. | Yes: Needs runtime verification |
| `NAV-REQ-019` | `frontend/src/app/(dashboard)/hr/page.tsx`, `frontend/src/lib/routePermissions.ts` | `/hr` root had no page (404 on direct navigation) while `routePermissions` allows it; the sidebar only links the four sub-pages. Resolved in QA round 3 (`QA3-05`) with a redirect stub to `/hr/attendance`. | Every path allowed by `routePermissions` SHALL resolve to a page or a redirect stub — no dead 404 routes. | WHEN a route is added to `routePermissions` THEN navigating to it directly SHALL render a page or redirect, never a 404. | No (fixed, statically verifiable) |
| `NAV-REQ-020` | `frontend/src/components/dashboard/AttentionAlerts.tsx` | A failed `/api/dashboard/alerts` request renders nothing, and a background refresh failure hides cached alerts. | The dashboard SHALL distinguish a successful empty response from a load failure, show a compact Arabic error with retry, use a safe server message when available, and preserve cached alerts during background failures. | WHEN the initial request fails THEN an Arabic error and retry SHALL remain visible; WHEN a refresh fails after alerts loaded THEN those alerts SHALL remain visible beside the failure notice; WHEN a successful response is empty THEN the genuine no-alerts state MAY render. | Yes: initial live success verified; failure paths covered by regression tests and need post-deploy runtime verification |
| `NAV-REQ-021` | `frontend/src/app/(dashboard)/page.tsx` | The recent-patients section initializes with an empty array and no independent loading state, so it displays “لا يوجد مرضى بعد” while the patient request is still pending. | The dashboard SHALL show a compact loading placeholder until the recent-patients request settles, then render either the real empty list, patient rows, or the existing error state. | WHEN `/api/patients?pageSize=5&status=active` is pending THEN the recent-patients empty message SHALL NOT render; WHEN it succeeds with an empty list THEN the genuine empty message SHALL render. | Yes: code-proven and covered by a deferred-response regression test; needs post-deploy runtime verification |
